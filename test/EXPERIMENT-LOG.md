# Asset-gen experiment log

Журнал рішень і висновків по інтеграції image-gen у playable-forge.
Кожен запис — що змінили + чому + результат. Використовувати як досвід для наступних ітерацій.

---

## 1. Вибір моделі (OpenAI)
- **Тестували:** `gpt-image-1`, `gpt-image-1.5`, `gpt-image-2`.
- **Рішення:** беремо **`gpt-image-1.5`** — найкращий баланс якість/стиль, прозорість з коробки.
- **Чому:**
  - `gpt-image-1` — соковито, але "чанкі", трохи гірший за текст/деталі.
  - `gpt-image-2` — **немає прозорості** (RGB, треба bg-removal) + у 3–4 рази повільніший (43–78с проти ~17с). ❌ не для UI.
- **Факт:** прозорий PNG (RGBA, colortype 6) у 1/1.5 робиться нативно через `background:"transparent"` + `output_format:"png"`. Конвертер НЕ потрібен.

## 2. Промпт-інженерія (головний важіль)
A/B 5 стратегій на одному ассеті (`prompt-lab`), стилі Diablo II та Heroes III:
- **Переможець: IP-anchoring** — назвати референс-гру + клас ("in the exact visual style of Heroes of Might and Magic III … Knight hero"). Дає найавтентичніший стиль.
- keywords / "structured-атрибути" дрейфують у генерику (Diablo → Dark Souls). Темним стилям потрібен сильніший IP-якір.
- HoMM3 (яскраве, архетипне) стабільне у ВСІХ стратегіях; Diablo (темне) — ні.
- **Зашито в `composePrompt`:** IP-anchor (`brief.derivedFrom`) + isolation-clause.

## 3. Прозорий фон / чистий виріз
- Проблема "зайвого фону" була через **слабкий промпт**, НЕ через модель.
- Додали в промпт: `perfectly isolated on a fully transparent background, no scenery, no ground, no cast shadow, clean crisp alpha edges`.
- **Результат (заміряно по альфі):** брудний ореол впав з ~7% до **<1%** (кнопки 0.2–0.55%). bg-removal майже не потрібен.
- "Сірий фон" у переглядачі картинок — це він малює прозорість на сірому тлі, а не запечені пікселі. Перевіряти альфу інструментально (`sharp`), не на око.

## 4. Rate limit
- **OpenAI gpt-image: 5 зображень/хв** на організацію → 429.
- **Рішення:** у `run.ts` додано **retry з backoff** (парсить "try again in Ns") + **skip-existing** (повторний запуск доганяє лише відсутні; `--force` щоб перегенерити все).

## 5. Вага ассетів (критично для 2MB playable)
- Сирий вивід: 1024×1024 PNG ≈ **1.4 MB** кожен. 12 шт ≈ 16 MB. ❌
- **Конвеєр:** `sharp` → `.trim()` (зрізати прозорі поля) → `.resize()` до дисплейного розміру (кнопки 360px, іконки 150px) → **WebP** (q80, alpha 90).
- **Результат:** кнопка ~25 KB, іконка ~10 KB. 12 ассетів = **210 KB** (було 16 MB).
- Single-file HTML з base64-інлайном = **376 KB = 18.3% від 2MB**. ✅
- Висновок: WebP з альфою + trim+resize — обов'язковий крок. base64 додає ~33%, закладати в бюджет.

## 6. Архітектура (стан)
- `src/assetgen/brief.schema.json` — канонічна схема стилю (enum-и + опис кожного поля).
- `styles/*.brief.json` — версійні брифи (diablo2, heroes3, bold-arcade).
- `src/assetgen/compose.ts` — `composePrompt(brief, asset)` + deep-merge override-ів (null = видалити поле).
- `src/assetgen/run.ts` — паралельний пул (concurrency 3) + retry + skip-existing + sidecar `.json` біля кожного PNG (повний промпт + версія брифа = відтворюваність) + HTML-звіт.
- `src/assetgen/prompt-lab.ts` + `labs/*.json` — A/B стратегій промпту.
- `src/assetgen/build-test-playable.ts` — оптимізація + збірка single-file playable.

## 8. Нормалізація кнопок (важливо!)
- **Проблема:** per-asset генерація дає КОЖНІЙ кнопці свою рамку, форму, колір каменю і "шрифт" (текст домальовує модель щоразу інакше). Однаковості так не досягти.
- **Рішення (обране): composite — рамка + шрифт.** Генеруємо ОДНУ пусту рамку (`btn-frame`, без тексту), переюзаємо для всіх кнопок, текст накладаємо реальним шрифтом (CSS/canvas).
- **Результат:**
  - ідеальна однаковість рамки + шрифту,
  - вага впала ще: 1 рамка (11 KB) замість 6 кнопок → ассети 70 KB, HTML **273 KB (13.4% від 2MB)**,
  - текст локалізується/міняється динамічно (важливо для playable під різні мови),
  - текст стилізуємо під гравірування (gold + emboss text-shadow); для крос-девайс однаковості — вшити fantasy-шрифт (Cinzel ~15KB woff2).
- **Альтернатива (не обрана):** `images.edit` від майстер-кнопки — зберігає AI-гравіювання, але дорожче (виклик на кнопку) і важче (кожна кнопка — окреме зображення).
- **Принцип на майбутнє:** усе, що має бути однаковим (рамки, плашки, фрейми) — генерувати ОДИН раз як шаблон і переюзати; варіативний контент (текст, емблеми) накладати окремим шаром.

## 9. Компонентний дизайн (розвиток принципу нормалізації)
Узагальнили "шаблон + контент" у компонентну систему. Шаблони генеруються РАЗ, контент накладається шаром.
- **Згенеровані шаблони:** `btn-frame`, `panel-frame`, `bar-track`, `avatar-frame`, `banner` (усі з `NO text`, прозорий фон).
- **Ключова техніка — 9-slice через CSS `border-image`:** один малий ассет розтягується в БУДЬ-ЯКИЙ розмір без спотворення кутів. Slice-значення рахуються автоматично з розмірів ассета (`build-components.ts`).
- **Компоненти:**
  - `Button` — btn-frame 9-slice + текст (OK / CANCEL / NEW GAME / CONTINUE CAMPAIGN з однієї рамки, будь-яка ширина/висота).
  - `Panel` — panel-frame 9-slice контейнер під будь-який контент.
  - `ProgressBar` — bar-track 9-slice + CSS-градієнт fill (fill = 0 KB). Нюанс: border-image з'їдає content-box → fill робити дитиною з `height:100%`, не `%` від padding-box.
  - `ResourcePill` — той самий panel-frame 9-slice, тонший border + іконка + число.
  - `AvatarFrame` — avatar-frame (прозорий центр) поверх портрета, `border-radius:50%`.
  - `Banner` — banner + заголовок шаром.
  - `IconButton` — круглі іконки.
- **Вага:** весь кіт (5 шаблонів + 6 іконок + портрет) = 154 KB, showcase HTML = 281 KB (13.7% від 2MB).
- **Принцип:** не генерувати кожен елемент окремо — генерувати МІНІМУМ шаблонів (frame/track/ring) і збирати UI композицією. Менше ассетів = менше ваги + ідеальна консистентність + динамічний контент.
- Showcase: `test/components/index.html`.

## 10. Переюзний кіт-модуль + інтеграція
- **`src/assetgen/kit/kit.ts`** — єдине джерело компонентів:
  - `loadKit(srcDir, opts)` — оптимізує шаблони (trim+resize+webp) + рахує 9-slice; `extra` для cover-зображень (портрет).
  - `makeKit(assets, {font})` — повертає `.css` + render-функції `banner/button/iconBtn/panel/bar/pill/avatar`.
- **DRY:** і playable, і showcase будуються з того самого кіту. Правка в кіті (напр. `white-space:nowrap` на кнопці) — фіксить усюди.
- **Інтеграція:** `build-test-playable.ts` тепер композить екрани з кіту (banner-заголовок, HUD-pill, panel із героєм+баром, кнопки). HTML = ~290 KB (14% від 2MB).
- Шрифт — параметр `makeKit({font})`, тому легко замінити на вшитий fantasy-шрифт.
- **Вшитий шрифт:** `fontFace(name, woff2Path)` інлайнить woff2 як base64 (`@font-face`). Вшито **Cinzel Bold** з Google Fonts — latin-subset лише **8 KB**, self-contained (без мережі), однаково на всіх девайсах. Це закриває крос-девайс варіативність системного serif.

## 11. Фон + персонаж у playable
- Згенерували `bg-castle` (HoMM3 kingdom vista, 1024×1536, opaque, high) як backdrop меню; повний лицар (`heroes3-knight/4-ip-anchored`) як персонаж на екрані героя.
- Виріз персонажа чистий поверх сцени (прозорий PNG → webp).
- **⚠️ Урок (вага):** фон-`url(dataURI)` НЕ інлайнити в кожен екран — це множить вагу. Було 5× → HTML 1022 KB. Винесли в ОДИН CSS-клас `.scene{background-image:url(...)}` → 477 KB. **Правило: великий ассет інлайнити РІВНО раз, посилатись класом.**
- Фон: webp 680px ≈ 102 KB, персонаж 520px ≈ 69 KB. Повний playable з фоном+героєм = **477 KB (23% від 2MB)**.

## 12. Референс-зображення (self-reference, images.edit)
- `ref-test.ts` — бере майстер-персонажа (heroes3 knight) як референс у `client.images.edit` (gpt-image-1.5, `toFile`) і генерує варіації póz.
- **Консистентність — відмінна:** обличчя, зачіска, броня, щит-лев, плащ ідентичні в усіх позах (меч угору / портрет / хода). → робочий спосіб робити **набір póz/емоцій одного героя**.
- **Ізоляція в edit слабша, ніж у generate:** прості повноростові пози лишаються чисті (halo 0.4%), але **bust/портрет схильний додати фон-вінʼєтку** (v2: 55% opaque, halo 2.4%) → для портретів вмикати `stripBackground()` або сильніший isolation-clause.
- **Кнопка-фрейм для UI має бути вертикально симетричною** — несиметричний шаблон (панель вгору на -12%) ламає центрування тексту. Перегенерували симетричну pill-рамку → offsetY -0.5%, текст став рівно. (Перевіряти симетрію `sharp`-аналізом, не на око.)

## 13. Прод-інтеграція в CLI (кроки 1–3)
- **Кіт-playable як CLI-команда:** `playable menu [styleId]` → `buildKitPlayable()` будує single-file, проганяє через `validate()` (Meta) і пише в `out/menu-<id>.html`. Результат: **PASS, 475 KB / 2048 KB**.
- **CTA / Meta (крок 2):** у playable вшито `FbPlayableAd.onCTAClick()` (CTA з `endCard()`) + локальний stub. Валідатор перевіряє: розмір ≤2MB, наявність CTA-хука, відсутність JS-редіректів і зовнішніх завантажень — усе зелене (фон/шрифт = data URI, не http).
- **Єдине джерело:** `buildKitPlayable` живе в `build-test-playable.ts`, CLI його імпортує (не дублює).
- **stripBackground (крок 3):** `kit.stripBackground()` через `@imgly/background-removal-node` (lazy-import), опція `strip:true` в `loadKit.extra`. **Працює, але на painterly-арті дає м'який матовий край (halo ~10%)** — модель тренована на фото. Висновок: для мальованих ассетів чистіше ізолювати на етапі генерації (isolation-clause), а strip тримати фолбеком для bust/портретів.

## 14. Адаптивна верстка (stage-scaler) + візуальні тести
- **Проблема:** флюїдна верстка (vw/vh/flex) "плаває" — reflow-иться по-різному на кожному екрані.
- **Рішення — `src/assetgen/kit/stage.ts`:** фіксований design-canvas `DESIGN = 400×860`, `#stage` масштабується
  (contain) під будь-який viewport через `transform:scale`, фон-сцена `cover` на `#viewport` заповнює gutters.
  Layout ідентичний скрізь — тільки масштаб. Kit перейшов на **фіксовані px** (прибрав vw/clamp).
- **Візуальні тести — `src/assetgen/visual-test.ts`** (Playwright, `npm run visual`):
  рендерить playable на 8 viewport-ах (360×640 … tablet 768×1024 … landscape 740×360 … square),
  робить скріншоти в `test/visual/` і **перевіряє, що жоден елемент не вилазить за viewport**.
  Результат: **ALL PASS на всіх 8**. Це обовʼязковий крок після будь-якої зміни UI.
- npm: `npm run menu` (білд playable), `npm run components` (showcase), `npm run visual` (тести).

## 16. Текст-оверлей сідає на писемну зону арту (авто, не фіксовано)
- **Проблема:** "REALM OF VALOR" вилазив за центр pixel-банера — писемна стрічка в кожного банера на різній висоті
  (heroes3 — нижче через золотий герб зверху; pixel — стрічка під стовпами). Фіксований padding не годиться.
- **Рішення (той самий принцип, що симетрія кнопки):** `bannerTitleY()` в `loadKit` міряє вертикальний центр
  насиченої смуги (зважено по к-сті насичених пікселів у рядку) → `makeKit` ставить заголовок на `top:titleY%`
  + горизонтальні поля 17% + `nowrap`. Працює для будь-якого банера без ручного тюну.
- **Правило:** текст-оверлей на згенерованому арті позиціонувати за **виміряною** писемною зоною, не за геометрією арту.

## 17. Візуальна ієрархія обʼєктів і текстів
- **Проблема:** усі кнопки меню були рівнозначні (+/- однакові) → око не розуміло головну дію.
- **Рішення — рівні в кіті:** `button(text, onclick, {level})` → `primary | (default) | tertiary`.
  - `primary` — більший фрейм/шрифт + золоте світіння + мʼякий brightness-pulse (головна дія/CTA).
  - `default` — звичайна вторинна дія.
  - `tertiary` — менша, приглушена (opacity .72), для другорядного (Exit).
- Застосовано: меню → New Game = primary, Exit = tertiary; на екранах головна дія (Begin Quest/Fight/Buy) = primary.
- **Правило:** не лишати елементи рівнозначними — кожен екран має 1 чітку primary-дію; другорядне приглушувати.
  Те саме для тексту (title > label > sub). Ієрархія — частина якості продукту, а не косметика.

## 18. Зонування layout (BASE ⊕ ARCHETYPE) + zone-асерти
- **Проблема:** розміщення компонентів було ad-hoc → криво. Рішення заземлене на UX-прийор-арт:
  thumb-zone (Hoober: primary CTA — низ-центр), Meta safe-zones, tap ≥44px.
- **`src/assetgen/kit/layout.ts`:** `BASE` (універсальні зони hud/title/stage/actions/footer + safe-поля + правила)
  ⊕ `ARCHETYPES[screenType]` (menu / pick-hero / endcard). `resolveLayout(type)` = deep-merge. Зони — частки DESIGN,
  scoped CSS під `.screen[data-type]`. Екран оголошує **явний screenType** (надійно; авто-класифікацію моделлю — пізніше на 10+ екранах).
- **Розміщення:** `zone("actions", button)` — компоненти лягають у дозволені зони, не в координати.
- **Debug-оверлей** зон (`#zones` у URL) — видно сітку/межі.
- **Zone-асерти у `visual-test.ts`:** кожен інтерактивний елемент має лежати у своїй зоні, primary CTA — у `actions` (thumb).
  Тести одразу впіймали, що HUD-смуга коротша за пілюлю/іконки → підправили висоти зон. Тепер ALL PASS (обидва стилі).
- Додано екран **endcard** (архетип endcard): великий герой + домінантний Install CTA (онклік `FbPlayableAd.onCTAClick`).
- **Правило:** не вигадувати координати — класифікувати тип екрану і брати готову зонну сітку архетипу; смуги мусять вміщати контент (перевіряє zone-асерт).
