# Дві системи композиції — коли яку юзати

У проєкті свідомо співіснують **дві** системи побудови екранів. Вони не конкурують —
у них різні задачі. Спільний фундамент — зони (`kit/layout.ts`) і компоненти (`kit/kit.ts`).

```
                 ┌─────────────────────────────────────────┐
                 │  kit/kit.ts (компоненти)                 │  ← спільне
                 │  kit/layout.ts (зони + 10 архетипів)     │  ← спільне
                 └───────────────┬───────────────┬──────────┘
                                 │               │
                ┌────────────────▼──┐   ┌────────▼─────────────────┐
                │  СИСТЕМА A         │   │  СИСТЕМА B               │
                │  layouts/ шаблони  │   │  groups → flow → recipes │
                └────────────────────┘   └──────────────────────────┘
```

## Система A — `layouts/` (шаблони екранів)

**Для чого:** рекламні playable-екрани (endcard, feature-grid, tap-reveal, …) — переважно
статична подача + одна головна дія (Install). Це 11 наших шаблонів.

**Контракт:** файл у `src/assetgen/layouts/`, об'єкт типу `Layout`:
- `meta.zoneTypes` — який архетип на кожному екрані
- `meta.assets` — які ассети потрібні (M-02)
- `screens(k, a)` — HTML через `zone("actions", …)`
- `pageCss()` — лише візуал (спільне — у `kit/screen-css.ts`)

**Білдер:** `build-test-playable.ts` (`npm run menu <style> <layout>`).
**Перевірка:** `npm run visual` + `check:layouts`.
**Додати новий:** кинути файл + 1 рядок у `layouts/index.ts`.

## Система B — `groups`/`flow` (інтерактивні ігри)

**Для чого:** ігрова логіка зі станами й переходами — tap-to-attack, drag-to-connect.
Там важливий **потік** (flow) і **правила композиції** (groups), а не просто статичний екран.

**Складові:**
- `kit/catalog.ts` — «біблія» компонентів (що є + як генерувати)
- `kit/groups.ts` — семантичні родини + `composeScreen` + `validateRecipe` (1 фокальна дія)
- `kit/flow.ts` — блюпринт екрана (purpose/scene/mechanic/transitions) + `validateFlow`

**Білдери:** `build-game.ts` (`npm run game`), `build-connect.ts` (`npm run connect`),
`build-recipes.ts` (`npm run recipes`), `catalog-doc.ts` (`npm run catalog`).

## Як вибрати

| Питання | Відповідь → система |
|---|---|
| Це рекламний екран з однією дією (Install)? | **A** (`layouts/`) |
| Тут є ігрова механіка / стани / перетяг / реальний геймплей? | **B** (`groups`/`flow`) |
| Треба багатоекранний тур по UI? | **A** — див. `showcase.ts` |
| Треба новий компонент-цеглинка? | додай у `kit/kit.ts` (обидві системи отримають) |
| Треба нову зону/архетип? | додай у `kit/layout.ts` (обидві отримають) |

## Статус (рішення M-03)
**Лишаємо паралельними.** Уніфікація під єдиний контракт — можлива в майбутньому
(коли стане ясно, куди розвивати ігри), але зараз не виправдана: системи стабільні,
розв'язані й покривають різні задачі. Спільне (зони, компоненти, CSS) уже не дублюється.
