02

Конфлікти й дрейф

Місця, де код і документація розповідають різні історії, або один термін означає дві речі. Це найдешевший шар для виправлення з найвищим вкладом у "припинити дрейф".

C1 · README ⟂ CLI
README заявляє 2D-модель templates × styles, але CLI реально 3D з --layout. Реальність ширше за документацію.
C2 · README × 2 однакові
forge-integrate/README.md і repo/README.md ідентичні, але CLAUDE.md у них різні (forge-integrate знає про PDS, Skills, layouts; репо — ні).
C3 · "Two styles ship" — насправді 9
README хвалить "Heroes III + Pixel Quest". У styles/ 9 брифів. Декларація вужча за реальність.
C4 · Два entrypoint-и
npm run menu (test-shortcut) у README як головне vs npm run forge (production) у skill-doc.
C5 · "Mechanic" перевантажене
У коді mechanic = templates/<id> (stubs). У маніфесті mechanic = Tower Defense/Match-3. Не сумісно.
C6 · "Brief" × 2 формати
briefs/*.json (legacy) vs styles/*.brief.json (current). Одне слово, дві сутності.
C7 · ROADMAP vs Manifest
ROADMAP — про вилизування існуючих layouts (Z-01..Z-09). Маніфест — про побудову нового верхнього шару. Не суперечать, але не зустрічаються.
C8 · Hardcoded 13 keys
Кожен стиль ВИМАГАЄ всі 13 ассет-ключів. Динамічне планування ассетів зараз архітектурно неможливе.
C9 · gh-pages артефакти
Багато menu-cyber-heist-*.html у gh-pages-deploy без явного відтворюваного процесу. Можливо демо, можливо мертві.
C10 · 2 worktrees
forge-wip/ + forge-integrate/ + repo/. ROADMAP I-06 каже прибрати перші два після merge.
03

План реалізації · фази 0–6

Деталі — у plan.md. Кожна фаза commit-able окремо; жодна не переписує існуюче, всі надбудовують. Сильна частина системи (asset-gen, kit, zones, validator) — недоторкана.

P0 · 1–2 дні

Stop the drift

До будь-якої нової роботи

Привести документацію у відповідність до коду. Усунути онтологічні дублі.

  • Переписати README під 3D-модель і forge-entrypoint
  • Перейменувати npm run menu → npm run dev:smoke
  • Видалити legacy briefs/*.json + команду playable build
  • Перейменувати mechanic (template-дир) → template
  • Прибрати forge-wip/ після merge
P1 · 3–5 днів

Brief stage

Після фази 0

Додати верхній шар: ніша + хук + механіка-кандидат → структурований Brief.

  • Тип UserBrief
  • mechanics-catalog.json як таблиця рішень
  • Агент planner.brief
  • Версіонування промтів: prompts/planner-brief/vN.txt
  • CLI playable brief <niche> …
P2 · 4–6 днів

Screen / Flow planner

Після фази 1

Brief → план екранів + флоу + hook. Артефакт _plan.json як early gate перед asset-gen.

  • Типи ScreenPlan / FlowPlan / Hook
  • Агенти planner.flow, planner.screens
  • hooks-vault.json — бібліотека гачків
  • Інтеграція у forge як Phase 0
P3 · 3–4 дні

Dynamic component breakdown

Паралельно з P2

Відмова від хардкоду 13 ключів. Ассети — функція плану.

  • Тип ComponentSpec
  • Агент planner.components
  • Розділити universal vs per-archetype rules
  • Адаптувати compose.ts під динамічний breakdown
P4 · 5–7 днів

Multi-agent orchestrator

Після P1–P3

Те що є — оформити як систему агентів. Версіонувати промти, додати rollback.

  • Тип Agent<I, O>
  • DAG orchestrator з паралелізмом
  • prompts/<agent>/vN.txt + playable prompt diff
  • Сидекари результатів агентів
P5 · 3–4 дні

Reflection + variability

Після P4

Семантичний критик + правила в "range" (як просив юзер).

  • Агенти critic.plan, critic.build
  • Тип RuleRange {min, max, target}
  • Retry-loop з варіативністю
P6 · 5–7 днів · опційно

User-facing UI

Коли CLI стане замалий

Веб-UI з вибором, превʼю, re-roll, live-логом агентів.

  • Vite-based local UI
  • Streaming log агентів (SSE/WS)
  • Preview у iframe
  • Кнопка "re-roll" з тим самим Brief
≈ 25 днів

Підсумок зусиль

Без UI

Це план до маніфесту, не до "красиво". Кожен крок дає робочий артефакт. Жоден не блокує наступний на більш ніж 1 фазу.

  • P0 — must, в першу чергу
  • P1+P2+P3 — нова цінність юзеру
  • P4+P5 — інженерна зрілість
  • P6 — продукт-полиш
