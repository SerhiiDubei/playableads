# План реалізації: від поточного стану до маніфесту

**Підхід:** фази нарізані так, щоб **кожна давала користь сама по собі**, не чекаючи наступних. Жодна фаза не "переписує все" — кожна додає шар поверх існуючого. Поточний робочий пайплайн (`forge` → menu-HTML) лишається живим увесь час.

**Легенда статусів:**
- ✅ Готово
- 🟨 Частково
- 🟥 Відсутнє
- ⚠️ Конфлікт

**Мета:** перетворити Brief на **план екранів** і **флоу між ними**.

**Що з'являється:** агент-планувальник екранів, типи `ScreenPlan` / `FlowPlan` / `Hook`, нова стадія між Brief і ассет-генерацією.

|---|---|---|---|
| 2.1 | Типи `ScreenPlan` (id, role, archetype, components-needed) + `FlowPlan` (screen graph) + `Hook` (первинний гачок: текст + візуал) | `src/agents/types.ts` | 1.1 |
| 2.2 | Агент `planner.flow` — приймає ResolvedBrief, повертає FlowPlan (граф екранів з ролями: hook → onboarding → engagement → endcard) | `src/agents/planner-flow.ts` | 2.1, 1.3 |
| 2.3 | Агент `planner.screens` — для кожного вузла графа повертає ScreenPlan (компоненти, копія, layout-archetype, дії на екрані) | `src/agents/planner-screens.ts` | 2.2 |
| 2.4 | Hook-vault: бібліотека шаблонів гачків (low-flow 1-2 дії vs deep-flow 15-30s) | `data/hooks-vault.json` | 2.1 |
| 2.5 | Інтеграція в `forge`: новий етап Phase 0 = `planner.brief → planner.flow → planner.screens` перед Phase 1 | `src/cli.ts:cmdForge` | 2.3 |

**Артефакт фази:** після `playable forge <brief>` спочатку з'являється `_plan.json` з повним розкладом екранів і потоку, **перед** тим, як викликати дорогу asset-gen фазу. План можна прочитати, відредагувати руками, або не схвалити (early gate).

**Перевірка готовності:** для одного й того самого Brief два прогони дають **різний, але узгоджений** план (варіативність у "range", як хотів користувач).

## Загальна часова оцінка

| Фаза | Робота | Ціна провалу |
|---|---|---|
| 0 | 1-2 дні | дуже висока (триватиме дрейф) |
| 1 | 3-5 днів | висока (нема входу в систему) |
| 2 | 4-6 днів | висока (нема плану між Brief і ассетами) |
| 3 | 3-4 дні | середня (без неї працює, але хардкод) |
| 4 | 5-7 днів | висока (без неї агенти невидимі) |
| 5 | 3-4 дні | середня (без неї немає рефлексії і варіативності) |
| 6 | 5-7 днів | низька (CLI достатньо) |

**Усього без фази 6:** 19-28 ідеальних робочих днів. З фазою 6: до 35 днів.

## Принципи виконання

1. **Кожна фаза commit-able окремо.** Між фазами система працює.
2. **Фаза 0 — обов'язкова в першу чергу.** Не починати фазу 1 поки фаза 0 не закрита.
3. **Не переписувати ассет-ген, kit, layout, validator.** Вони — фундамент. Лише надбудовувати.
4. **Фази 1-2 можна писати під дешевим model-ом** (gpt-mini), бо це структуроване перетворення JSON → JSON.
5. **Фаза 4 — рефакторинг, а не нове.** До неї агенти існують як функції. Після — як інстанси `Agent`.
6. **Кожен новий агент — з версіонованим промтом з першого дня.** Уникнути ретроактивне версіонування.

## Що НЕ робити

- Не міняти Meta validator — він пройшов жорсткі вимоги мережі.
- Не міняти zone-engine — це найкраща частина системи.
- Не торкатися `kit.ts` без візуальної регресії (вже фіксована).
- Не плодити нові термінологічні дублі (як було з "Brief").
- Не додавати features за списком "було б непогано" — будь-який feature, що не наближає до маніфесту, відкладається.
